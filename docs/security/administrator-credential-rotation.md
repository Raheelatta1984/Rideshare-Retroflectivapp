# Administrator credential rotation — out-of-band runbook

**Status: not done by this repository, and it cannot be.** Every item below
happens in an account, a provider console or a deployment you control. Code can
remove a literal from a file; it cannot un-leak a password that has been public
in a git history since the commit that introduced it.

Two facts drive the order of work:

1. The literal that shipped in `src/lib/access.ts` was **a real person's email
   password**, not a disposable demo value. It has been in a public repository,
   so assume it is in someone's wordlist.
2. Removing it from the current tree does not remove it from history. Rewriting
   history does not undo distribution. Only a password change does.

Treat the credential as compromised until step 1 is complete.

---

## 0. Before you start (10 minutes, read-only)

| Check | How |
| --- | --- |
| Where does this password work? | Anything signed into with that address: the mailbox itself, app stores, social accounts, the Supabase project, hosting, DNS, the domain registrar. |
| Was it reused? | Search the password manager for the address, not the password. Every hit is in scope. |
| Is there a second factor anywhere? | If not, add it **before** changing anything — the mailbox is the recovery path for everything else. |
| Who else knows it? | Anyone who has read this repository, cloned it, or received a build artifact. Do not attempt an enumeration; assume "anyone". |

Do not rotate the mailbox password first and leave 2FA off. Losing the mailbox is
worse than losing the password.

---

## 1. The identity provider (the actual leak) — ~15 minutes

The password in the repository is an **email account** credential. Rotate it
where it lives.

- [ ] Sign in from a known device on a known network.
- [ ] Change the password to something generated by the password manager
      (20+ characters, unique). Never type the old one to "verify" it later.
- [ ] Enable or re-confirm two-factor authentication (authenticator app or passkey,
      not SMS where a choice exists).
- [ ] Review **active sessions / devices** and sign out everything unfamiliar —
      then sign out everything, and sign back in only what you need.
- [ ] Review **recent security activity** (sign-in history, recovery-email and
      forwarding changes, app passwords, OAuth grants). Note the window between
      the commit that introduced the password and now; anything in that window
      from an unfamiliar location is an incident, not a chore.
- [ ] Check recovery options and app-specific passwords; revoke any app password
      created in that window.
- [ ] If the provider offers it, turn on **login alerts**.

Write down the date/time of the change. That timestamp is the boundary you will
use in the audit below.

---

## 2. Every other service that accepted that password — ~20 minutes

Work through the password manager's hits for that address.

- [ ] Change the password on each one (unique each time).
- [ ] Sign out all sessions on each one.
- [ ] Revoke API tokens, personal access tokens and app passwords issued before
      the rotation date. A password change does not invalidate those.
- [ ] Where the service records it, review sign-in history since the leak.
- [ ] For anything holding payment details, check for new payment methods or
      saved-card changes.

---

## 3. This application's own credentials — ~30 minutes

These are separate from the personal account, and all of them are affected by
the same leak window because they lived in the same repository or deployment.

### 3.1 Supabase auth users

If the leaked address also exists as a Supabase user in the project, rotate it
with the provided script (it uses the Admin API, never the browser):

```bash
export SUPABASE_URL="https://<project>.supabase.co"
export SUPABASE_SERVICE_ROLE_KEY="<service role key>"   # server-side only
node scripts/rotate-admin-credential.mjs --email <address> --dry-run
printf '%s' "$NEW_PASSWORD" | node scripts/rotate-admin-credential.mjs \
  --email <address> --apply --password-stdin --revoke-sessions
```

- [ ] Dry run first: it prints the user id, creation date and last sign-in.
- [ ] Apply, then confirm the script reports "the new password authenticates".
- [ ] If `--revoke-sessions` returns an error, rotate the project's **JWT secret**
      (Settings → API → JWT Settings → "Rotate"). That invalidates every access
      token in flight, including BFF sessions; users must sign in again.

### 3.2 Local booth accounts (browser-local)

The seeded administrator account is now created **without a password** and must
be activated through *Forgot password → email code → new password*.

- [ ] On each device that ever ran the old build, clear site data for the origin
      (or let the app migrate: a cleartext record is re-hashed on the next
      successful login, but that login uses the *old* password — change it).
- [ ] Do not "restore" the old password to save time on any device.

### 3.3 Reviewer role and stored sessions

Applying the access-control migrations and naming the reviewer is a deploy step,
not a code change:

```bash
DATABASE_URL='postgres://…' npm run db:harden -- --apply --grant-admin tic.raheel@gmail.com --revoke-sessions
```

- [ ] Run it after the rotation in 3.1 (the grant is idempotent; re-running is safe).
- [ ] `--revoke-sessions` deletes that account's stored BFF sessions, so the
      token issued before the rotation stops working on the next request.
- [ ] Sign the account in again — the role lives in the token.
- [ ] If the account is also a Supabase user whose password was rotated, do the
      rotation first so the new password is the one that gets used.

See `docs/security/rls-model.md` for the full ordering and the breaking changes.

### 3.4 Supabase API keys

- [ ] **anon key** — rotate if it was ever pasted anywhere other than the
      deployment's environment settings. It is public by design, but a rotated
      key shortens the window for anyone who built a client against the old one.
- [ ] **service_role key** — rotate unconditionally if it was ever in a file that
      could have been read by someone else. It bypasses RLS entirely.
- [ ] Update the deployment's environment (Vercel / the BFF host) with the new
      values, redeploy, and confirm the app still works before revoking the old
      key.

### 3.5 Other secrets in the same blast radius

- [ ] `BFF_CSRF_SECRET` — regenerating it invalidates outstanding CSRF tokens
      (harmless; users reload).
- [ ] `BFF_SESSION_KEY` — regenerating it makes every stored session unreadable,
      which is a valid "sign everyone out" mechanism.
- [ ] `BFF_MANIFEST_SECRET` — rotating it invalidates signed playlists; displays
      re-fetch on their next poll.
- [ ] `GITHUB_WEBHOOK_SECRET` — rotate, then update the webhook in GitHub.
- [ ] `VITE_TURN_*` credentials — rotate at the TURN provider.
- [ ] Database password — rotate in the provider, update `DATABASE_URL` and
      `BFF_DATABASE_URL`, then restart the data plane and the BFF.

## 4. Verification — do not skip

- [ ] The old password fails on every account where it was changed. Test **one**
      sign-in attempt per account, from the provider's normal page; more than a
      few failed attempts can lock the account.
- [ ] No active session predates the rotation (provider session list, plus
      `select * from public.bff_sessions` — the rows should be gone after a
      `BFF_SESSION_KEY` change or a JWT-secret rotation).
- [ ] The Supabase auth logs (Dashboard → Logs → Auth) show no successful sign-in
      for the account from an unfamiliar IP in the leak window.
- [ ] Postgres logs show no unexpected `approval_audit` or `campaigns` writes
      attributable to the account since the leak.
- [ ] The repository scan is clean *and* history is acknowledged:

```bash
# The literal must not be in the working tree.
git grep -n -iE 'password\s*[:=]\s*"[^"]{6,}"' -- . ':!*test*' ':!docs/*'
# It is still in history. This is expected; the rotation above is the control.
git log --oneline -S '<the old literal>' --all | head
```

- [ ] Record what changed, when, and by whom in the incident log.

---

## 5. What "done" looks like

| Item | Evidence |
| --- | --- |
| Mailbox password changed | Provider "password changed" confirmation, timestamp recorded |
| 2FA enabled | Provider security page |
| Other sessions signed out | Empty device list except known devices |
| Reused passwords changed | Password manager audit shows unique values |
| Supabase user rotated (if present) | `rotate-admin-credential.mjs` verification line |
| Supabase JWT secret rotated (if session revocation failed) | Dashboard confirmation + all users re-authenticated |
| Other secrets rotated | Deployment env diff, redeploy, smoke test green |
| Sign-in history reviewed | Screenshot or export attached to the incident log |

Until all eight rows have evidence, `docs/security/production-risks.md` keeps the
"leaked credential" risk marked **open** — the code-side hardening in this
repository is not a substitute for it.
